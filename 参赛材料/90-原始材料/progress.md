### 这一轮修掉的三个「隐蔽错误」

都是**画面能跑、不报错，只是看着怪**的那一类 —— 最容易被当成美术风格问题放过去。

| 现象 | 根因 | 修法 |
|---|---|---|
| 绿洲是**一块绿色贴片**，不是长出来的 | 地形格之间是硬边；上一轮试过过渡贴图但失败（`desert_light_*` 自带固定斑块、16px 格不能旋转朝向绿洲） | 改用**抖动**（逐像素/2×2 成簇混合两材质）。抖动**各向同性**，不需要朝向，这正是上一轮方案失败的原因所在 |
| 沙地上有**等距重复的浅色矩形**（墙纸） | `sand_base_03` 用 `SAND_MID` 当基色，比其余变体暗一档；平铺 880 次后色差变成网格 | 全部变体统一 `SAND_LIGHT` 基色，差异只来自细点。**同一个错误后来在雪地上又犯了一次**，已加回归护栏 |
| 草地上散着**突兀的青色方块** | `grass_pebble_01.png` 名字叫卵石，内容却是青蓝斑块；另两张 `gravel_01`/`dirt_patch_01` 其实是地形交界块 —— 三张都是整块不透明图，被当植被撒了满地 | 用 `make_props.py` 生成 7 张**带透明通道**的真点缀替换 |

### 一条值得记住的教训

**「过渡贴图」失败过一次，但失败的是那种具体做法，不是「过渡」这件事。**
上一轮的结论是「像素画里硬边读起来是干净的」—— 那个结论是错的，
它把「带固定斑块的装饰贴图不能用」错误地推广成了「过渡不能用」。

区分开这两件事之后，抖动方案一次就成了。**推翻一个方案时，要问清楚到底是哪一部分不成立。**

| 用途 | 结论 | 依据 |

| **事件卡插画** | **可行且效果好** | 不受像素网格约束、要的就是手绘感、显示尺寸够大（150x200）。与立绘同理 |

### 根因：两套 id 命名，交集为空

| numbers.json（建造用） | sites.gd（地图用） |
|---|---|


### ⚠ 事故：PowerShell 改写源码毁掉了整个文件的中文

批量替换几处裸数字时用了 `Get-Content -Raw` + `Set-Content`，结果
**`map_view.gd` 全部中文注释变成乱码并写入了 BOM**。根因：PowerShell 的 `Get-Content`
默认按系统 ANSI 代码页（中文 Windows 是 GBK）读取 UTF-8 文件，再按 UTF-8 写回。
**ASCII 部分毫发无损，所以语法测试照样全过**，是最难发现的那种损坏。

试过逆向还原（UTF-8 读 → 按错码页编码 → UTF-8 解码），`gb18030`/`cp936`/`gbk`/`big5` 全部失败 ——
GBK 解码对有损字节不可逆。最后 `git checkout` 恢复，用 `edit` 工具重做了全部改动。

**规矩**：改源码一律用 `edit`/`write` 工具；要批量替换就用 Python 显式 `read_bytes()/decode('utf-8')`。
事后自检：文件不该有 BOM、`'坎儿井' in text` 应命中、U+3400–U+4DBF 生僻字数应接近 0。

### 顺手修的方向反了的公式

`population_capacity()` 原本是 `min(..., housing)` —— 把住宿当**上限**。

住宿是"多出来的床位"，应当是**加成**，已改成 `min(水, 田) + 床位`。

> 结果实测是 12，顺着查才发现公式方向反了。

### 扩图牵出来的一个"巧合成立"的 bug

## 摆法对比探针：抓出「自动布阵反而是最烂的阵」（2026-10-06）

前面我一次次请玩家「打两场对比给我看」——那是把验证的活推给他，而且单场战斗伤害是

**做法**：同一批兵（盾2 弓2 乡1）、同一个敌人（4 人）、只换摆法，每种各跑 6 遍，
**每种摆法用同一组随机种子**（否则随机性会盖过摆法差异）。
加速手段是把 `_step_time` 从 0.62s 压到 0.015s（只改探针那一份实例，不写回 numbers.json）。

|---|---|---|
| **A 自动布阵（盾前/弓后）** | **2.17 ← 最差** | **1.00** |
| B 全员压最前线 | 0.00 | 0.00 |

### 抓到的真问题（#89）

**我那个"聪明的默认阵"是四组里最烂的一组。** 根因：盾卫在 x=726、弓手在 x=662，
**间距 64px，而弓手射程只有 52** —— 弓手够不到正在和盾卫交手的敌人，只能自己挪过去，
等它到位前排已经挨完打了。

修法：自动布阵改成**两条线**，近战在最前、弓手紧贴其后 20px（射程 52 覆盖前排外扩 32px）。
并加了一条**数据驱动的断言**守住它：`盾卫x − 弓手x < 弓手射程`。
光断言"弓手在盾卫后面"是不够的 —— 在后面但出了射程，等于没带弓手。

### 摆法现在真的影响结果了

差距 **0.00 ~ 3.00 人**（五人队伍里差三个人，60%）。而这批数据也暴露了模型的**性格**：

**「全员压上去」目前是最优解，纵深反而是负担。** 因为交手逻辑里**没有"挡"**——
后排够不到正在交手的敌人，散开就等于同一时刻投入战斗的人更少、被逐个击破。
所以「盾卫挡在前、弓手在后」这个**应该**成立的战术，现在只赢在"弓手没出射程"，

### 一、畜牧系统（新）

**核心设计：兵种按岗位分，牲畜按「派人去抓」来。** 牲畜不是凭空来的 ——
要么派人去草原抓野畜，要么等商队卖。这一条把已有但一直没接线的
`exploration.caoyuan`（草原牧场）和 `majiu.livestock_capacity` 都用上了。

|---|---|---|---|---|---|

| 吐鲁番鸡 | — | 3 | 0.2 | 4 天/70% | 禽蛋 |

**牲畜品种全部是新疆的真实品种**（阿勒泰细毛羊、绒山羊、双峰驼、库车驴、吐鲁番鸡），
野畜也是（天山盘羊、鹅喉羚、蒙古野驴、野驼）—— 新疆特色不是贴标签，是直接进数据。

**关键机制**：
- **草料折算成粮**：多养一头羊，人就少吃一份。这是「养多少牲口」的取舍所在
- **牧人决定产出**：1 个牧人照看 8 头；超出的按"没人管"算（产出减半、不繁殖）
- **冬季饲料 +30%**：要靠膘过冬
- **抓野畜**：成功率随"去过几次"上升（0.42 + 4%/次），失败**不扣人**、只白费一趟人工。
  失败要疼，但不该劝退
- 掉牲畜按「鸡→山羊→羊→驴→驼」的顺序，先死最不值钱的

**核心设计：每一种灾难都能被预判、被准备。** 候选按季节筛 → 掷骰 → 按 `mitigation`

### 四、三张动物素材整身是「水系蓝」（#97，第 9 次同类问题）

`animal_sheep_01` / `animal_donkey_01` / `animal_chicken_01` 三张图
**整身用了色板里的水系蓝**（`#8FC7D6` / `#5A9CB0` / `#3A7086`）——
干沙地上的蓝色羊看着就像故障色块。前两次是 `rock_small_01` / `rock_pile_01`。

成因（推测）：这三张从 tiny-farm 素材包转来时原图是白/灰色调，
按"最接近的调色板颜色"映射时，这个 34 色板里最接近白灰的那一段**本身就偏蓝**，
更亮的部位就落到了真正的水系蓝上。

修法：**按明度映射**到暖色段（和当初修石头同一招），保留明暗关系、只换色相。
改完三张图的偏蓝像素为 0，全部落在色板内。并写了
`scripts/pipeline/audit_animals.py` 专门查动物素材的用色 —— 动物颜色太多样，
肉眼在游戏里分不出"这只羊本来就是蓝的"还是"它跑色了"。

### 五、一个必须记住的工程坑：改素材要重新导入

改完源图后**游戏里还是旧的蓝色**。查了半天：

- 源图已经干净（0 偏蓝）
- 但画面上的动物仍有 2.8% 青蓝像素（`#4F7578`）
- `.godot/imported/*.ctex` 的时间戳还是**前一天**的

**根因**：Godot 的**运行时 binary 不会重新导入资源** —— 导入只发生在编辑器里
（或显式 `--import`）。所以**改了任何素材之后必须**：

```
Godot_v4.7.2-stable_win64_console.exe --path scripts --headless --import
```

跑完之后缓存时间戳刷新，画面才真的变。**这一条以前没记下来过，
所以前面每一次改素材其实都可能有过"改了但没生效"的窗口期。**

复检方式也记一下：不能只找**精确**色值 —— 项目开了线性过滤，
旧图和过滤混色都会绕过精确匹配。要用**"蓝分量明显大于红分量"**这种稳健判据。

### 三、节庆：诺鲁孜节 / 葡萄熟了 / 古尔邦节（#100）

用真实的新疆节庆。判据只有「季 + 季内第几天」，**刻意不加随机** —— 节庆要可预期才像个日子。
用 `flags` 记住今年过过了，防止反复推进时段刷声望。

古尔邦节还有一条：**家里牲口够多（≥5 头）声望多 +4**。
「养牲畜的回报不只是钱」这句话得真的落在数值上才算数。

### 四、抓到一个「永远触发不了」的节日（#101）

古尔邦节原本写在**秋季第 40 天**，而 `calendar.days_per_season` 是 30 ——
代码里 `in_season = ((day - 1) % 30) + 1` 永远算不出 40，
所以**这个节日一次都不会触发**。

它的可怕之处是**完全静默**：数据合法、代码不报错、原有测试也全绿，
只是那个节日悄悄地不存在。**这是数据驱动系统最典型的失效方式。**

修法：日期改 25，并加一条静态自检断言（所有节日的 day 必须落在 `1..days_per_season` 内）。

### 一、木卡姆（#102）

数据在 `numbers.json` 的 `music` 段。价值不在"加士气"，而在于**把三条已有系统串成一条链**：

```
木料（采集）→ 作坊做热瓦普（加工）→ 奏乐台办木卡姆（士气 / 声望）
```

六套曲目全部取自**真实的十二木卡姆**（拉克 / 且比亚特 / 木夏吾莱克 / 恰尔尕 /
潘吉尕 / 乌孜哈勒），并在数据里写明是十二套里的六套，不假装都做了。

办一场的条件：奏乐台在场 + **木卡姆艺人在场** + 库里 1 把热瓦普（**不消耗**）
+ 2 行动点 + 1 个闲人，办完冷却 3 天。
热瓦普不消耗是刻意的：用完就断弦要重做的话，玩家会不敢办，这条链等于废了。

**入口是点地图上的奏乐台**，不是右栏再加按钮（右栏已排到 230/232，塞不下）。
为此给 `map_view` 加了 `site_pressed(site_id)` 信号 —— 而且**刻意不消费这次点击**：
别处可能还要处理，被吞掉会变成很难查的"某个位置点了没反应"。

### 二、艾德莱斯绸与棉花（#103）

- **棉花**：秋收，每名农夫额外 2 单位（新疆棉花就是秋收，和葡萄同期）

## 修 bug（2026-10-06）：两个「只有老玩家才会遇到」的 bug

用户只说「帮我检查并修复一下 bug」，没说具体是哪个。按既定策略**先写边界用例把真问题逼出来**，
不凭猜改代码。371 项既有断言全过，说明问题在**没有覆盖到的场景**里。

### Bug 1：读旧存档会让「大改」之后的系统全部失效（#109）

`load_from()` 原本是 `state = parsed["state"]` —— **整体替换、没有迁移**。
而本项目每一轮都在加系统（畜牧 / 灾难 / 加工 / 节庆 / 木卡姆 / 畜栏），
所以**旧存档里根本没有 `livestock`、`disaster`、`music_cooldown`、`products`、
`wild_trips`、`karez.reservoir_level` 这些键**。读出来之后：

- 畜牧：`state["livestock"]` 是 null → `_tick_livestock()` 直接报错
- 灾难：`state["disaster"]` 是 null → 掷灾与通告全失效
- 木卡姆：`music_cooldown` 缺失 → 冷却判断读到 null

**这个 bug 的隐蔽之处**：新开一局永远正常，只有读旧档才炸；
而所有测试都是新开一局，**从来不读旧档** —— 于是 371 项断言全绿。

**修法**：`load_from` 里加一次 `_merge_defaults(state, _initial_state())`
（递归、**只补缺失的键、绝不覆盖已有值**），并保留原有的 clamp 与事件恢复。

### Bug 2：建造菜单只有 2 座建筑，而数据里有 13 座（#110）

`hud.gd` 里硬编码了：

```gdscript
const BUILDINGS := [
    {"id": "yiguan", "name": "驿馆"},
    {"id": "majiu",  "name": "马厩"},
]
```

而 `numbers.json` 里已经有 **13 座**。于是**仓库 / 厨房 / 巴扎 / 作坊 / 晾房 /
围墙 / 烽燧 / 居所 / 毡房区 / 奏乐台 / 畜栏全都不会出现在菜单里，玩家根本点不到。**

更糟的是：这两个建筑的 gate 也是 `sections >= 2`，而我早先给 `build_info` 加了
「已在起作用就拒绝」——**所以段数过了 2 之后，菜单里两项全是「此地已有」，整个建造菜单等于废的。**

**修法**：
- `game_state.all_buildings()` 从数据取有序列表
- HUD 的菜单改成**数据驱动 + 分页**（右栏可视高度只有约 168px，13 行放不下 → 每页 5 行，
  上一页/下一页，灰掉的项把鼠标停上去能看到原因）
- 判据仍然只在 `build_info()` 一处，HUD 只负责渲染

### 这一轮为什么没早发现

两条都属于同一类：**「数据里有、代码不读」的静默失效**。
这是本项目第 10 次遇到（前面 9 次：`majiu.livestock_capacity`、食物 `shelf_life_days`、
`cangku.spoilage_reduction`、`karez.reservoir.levels`、4 个地标定义、
晾房 `fruit_to_raisin_rate`…）。

区别在于前 9 次都是「字段没人读」，而这次是**「列表没人同步」和「存档没人迁移」**——
形态不同、根因一样：**代码里另写了一份本该从数据来的东西**。

## 美术踩坑（三则，都是同一类错误）

| 现象 | 根因 | 修法 |
|---|---|---|
| 沙漠像**墙纸** | 拿**地形过渡贴图**当底纹（`desert_light_01/02` 各带一块装饰斑块） | `make_ground.py` 程序化生成纯底纹；过渡贴图改用在交界处 |
| 草地有**等距重复的浅色弧线** | 同上，`grass_*` 底图自带重复特征，平铺 880 次后显形 | 同上 |
| **树不像树**，是一坨绿块 | 把 **tileset 碎片**（大树树冠的四分之一）当成独立树；另有两张是**完全空图** | `make_trees.py` 生成完整树（橡树/白杨/胡杨）；只用已验证完整的贴图 |
| 「农田」里长的是**木桶、石堆、一张脸** | 照低分辨率标注图目视识别后**心算** `n = row*12 + col`，算错格 | 渲染放大网格、**每格标真实编号**再挑；`reextract_tiles.py` 重提 |
| 树看着**浮空 / 各飘各的** | 精灵用 `centered=true` 定位，48px 的树一半伸到格点下方 | `_add_tree()` 改根部落地（底边贴格点） |

**共同教训**：像素素材**必须按编号与尺寸核对**。
这类错误很隐蔽 —— 画面能跑、不报错、绿洲照常长大，只是「看起来怪」，
最容易被当成美术风格问题放过去。

**验证素材是否可用的两个快速检查**：
```
不透明像素占比 = 0  ->  空图（tree_pink_01 / tree_small_02 就是这样）
四边贴边 + 内部有多块互不相连的形状  ->  大概率是 tileset 碎片
```
